Nextflow / input:

input:

tipo/sintaxislang/nextflow

Es la entrada del pipeline, la información con la que va a jugar, Nextflow es muy bueno para manejar esta información, simplemente lo lee de su archivo de configuración y usa esa información para ejecutar algún programa con parámetros bajo un nombre designado.

Cómo se ve

input:
tuple val(sample_id), val(fragment_path)
path state_in, stageAs: 'state_in'

Los tres tipos que usamos

  • val — un valor suelto (un string, un número). Ejemplo: sample_id.
  • path — un archivo o carpeta. Nextflow lo monta dentro del -work-dir de la tarea (normalmente como symlink) antes de correr el script.
  • tuple val(a), val(b) — empaqueta varios valores en un solo item, para que lleguen juntos y emparejados. Así nunca te toca el sample_id de una fila con el fragment_path de otra.

De dónde viene la información (matiz)

De un canal, no del nextflow.config. El config es donde viven los params (rutas fijas, fecha de la corrida, cuánta memoria pedir), y esos sí los lees directo con ${params.algo} dentro del script sin declararlos como input. Los input: los alimenta el workflow cuando llama al proceso:

QC_RUN_ONE_SAMPLE(qc_samples, QC_GENERATE_COMMANDS.out.state.first())

Ahí qc_samples es un canal de ~20 items (uno por muestra) — y por cada item que llega, Nextflow dispara una ejecución nueva del proceso. Esa es la parte importante: el input: no solo dice QUÉ entra, también decide CUÁNTAS veces corre el proceso.

stageAs: — renombrar lo que entra

path state_in, stageAs: 'state_in' obliga a que la carpeta que llega se monte con el nombre state_in, venga como venga. Hace falta porque el proceso va a crear su propio state de salida y los dos nombres chocarían.

Ver también

  • output — el otro lado.
  • first() — cuando un input de una sola corrida tiene que alimentar N ejecuciones.
  • state_in — el nombre que usamos siempre para esto en el pipeline.
