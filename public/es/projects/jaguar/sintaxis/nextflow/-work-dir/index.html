Nextflow / -work-dir

-work-dir

tipo/sintaxislang/nextflow

Al principio yo hacía todo en una sola carpeta, y después terminaba con un relajo de archivos, outputs, inputs, figuras, todo en un solo lugar. La gente sensata de Nextflow ya sabía que esto está mal entonces para cada run del módulo se crea una carpeta llamada work que está separada por hashes, o el nombre único del workflow.

Qué hay adentro de un hash

work/a3/f91c8e7d2b.../
├── .command.sh      <- el script: ya interpolado, tal cual se ejecutó
├── .command.log     <- stdout/stderr
├── .exitcode
├── state_in         <- los inputs, montados como symlink
└── state            <- lo que el proceso produjo

El hash no es aleatorio: sale de los inputs + el script + el contenedor/env. Por eso -resume funciona — si nada de eso cambió, el hash es el mismo, Nextflow encuentra la carpeta y se salta la tarea en vez de recalcularla. Cambia una coma del script y el hash cambia, y esa tarea (y todo lo que venga después) se vuelve a correr.

El flag

Por defecto es ./work/ en donde sea que lances nextflow run. Con -work-dir lo mandas a otro lado:

nextflow run main.nf -stub-run -work-dir tmp_scratch/nf-stub-work

Útil justamente para que las pruebas de -stub-run no ensucien la raíz del repo, y para mandar el work a scratch en vez de a lustre.

Ojo con el espacio

El work dir no se borra solo y se hace enorme (guarda una copia de cada output intermedio de cada intento de cada tarea). Los inputs son symlink, así que no duplican, pero los outputs sí son archivos reales. Borrarlo es seguro una vez que lo que te importa ya salió por publishDir — a costa de perder el -resume.
