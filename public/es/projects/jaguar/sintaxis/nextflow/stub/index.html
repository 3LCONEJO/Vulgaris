Nextflow / stub:

stub:

tipo/sintaxislang/nextflow

Igual que -stub-run, es la parte en donde escribes lo que se va a ejecutar si activas el flag -stub-run, es como script pero falso.

Cómo se ve

process CONSENSUS_PEAK_CALLING {
    script:
    """
    cp -rL state_in state
    python .../02_consensus_peak_calling.py --out-dir state ...
    """

    stub:
    """
    cp -rL state_in state
    mkdir -p state/consensus_peak_calling
    touch state/consensus_peak_calling/consensus_regions.bed
    """
}

La regla para escribirlo

El stub tiene que crear exactamente los mismos nombres que declara el output del proceso, y nada más. Si el output dice path "state", emit: state, el stub tiene que dejar una carpeta state ahí parada. No importa que los archivos estén vacíos: lo único que se está probando es que la tubería conecte, no que los datos sirvan.

Por eso los stubs de este pipeline son casi siempre mkdir + touch + un cp del state_in.

Si el stub se olvida de un archivo, la tarea falla igual que fallaría en producción — y eso está bien, es justo el error que quieres ver en segundos en vez de en la hora 7.

  • -stub-run — el flag que lo activa.
  • Stub Run — cómo se validó todo el piloto con esto.
