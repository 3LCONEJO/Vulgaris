Nextflow / QC RUN ONE SAMPLE

QC RUN ONE SAMPLE

tipo/procesojob/customenv/pycistopic

nf/modules/a_pycistopic/qc_run_one_sample.nf

process QC_RUN_ONE_SAMPLE {
    label 'pycistopic_env'
    tag "${sample_id}"
    publishDir "${params.project_root}/3_output/${params.run_date}/A_pyCisTopic", mode: 'copy'

    input:
    tuple val(sample_id), val(fragment_path)
    path state_in, stageAs: 'state_in'

    output:
    path "state", emit: state

    script:
    """
    cp -rL state_in state
    python -m pycisTopic.cli.pycistopic qc \\
        --fragments ${fragment_path} \\
        --regions state/consensus_peak_calling/consensus_regions.bed \\
        --tss state/1_qc/tss.bed \\
        --output state/1_qc/${sample_id}
    """
}

tuple val(sample_id), val(fragment_path) — dos valores en un solo input

Ya viste val sample_id solo (un string) en build_cistopic_objects.nf (BUILD CISTOPIC OBJECTS). Hace falta ADEMÁS la ruta de fragmentos de esa muestra puntual, porque el comando de pycisTopic la necesita como argumento (--fragments) — no alcanza con el nombre de la muestra. tuple val(a), val(b) empaqueta los dos juntos en un solo item de canal, así que cada vez que llega uno nuevo, Nextflow dispara una ejecución con AMBOS valores correspondientes a la misma fila (nunca el sample_id de una fila con el fragment_path de otra).

De dónde sale qc_samples — reconstruir el CLI de pycisTopic a mano

// en pycistopic.nf
qc_samples = fragment_mapping
    .splitCsv(header: true, sep: '\t')
    .map { row -> tuple(row.dataset, row.fragment_path) }

QC_RUN_ONE_SAMPLE(qc_samples, QC_GENERATE_COMMANDS.out.state.first())

Se decidió armar el comando python -m pycisTopic.cli.pycistopic qc ... DIRECTO (mismos flags que 03_qc_generate_commands.py ya escribe en pycistopic_qc_commands.txt) en vez de parsear ese archivo línea por línea para extraer la línea de una muestra puntual — parsear texto generado por otro script para volver a separarlo es más frágil que simplemente reconstruir el mismo comando con los datos que Nextflow ya tiene a mano (sample_id, fragment_path, y las rutas fijas (Obtenidas a partir de QC GENERATE COMMANDS con la funcion first()) consensus_regions.bed/ tss.bed dentro de state). El archivo pycistopic_qc_commands.txt sigue generándose igual (por 03_qc_generate_commands.py, sin cambios) — queda como documentación de qué comando correspondía a cada muestra, aunque ya no sea lo que efectivamente se ejecuta.

Recursos: por qué 100GB por muestra, no menos

nextflow.config’s withName: QC_RUN_ONE_SAMPLE le da 100GB/muestra y maxForks = params.max_parallel_qc (6). Ese número no es una estimación a ciegas: viene de que el intento anterior (secuencial) ya había medido un pico real de 65.1GB procesando una muestra a la vez — como bash pycistopic_qc_commands.txt corría los 20 comandos uno detrás del otro (no en simultáneo), ese pico YA es representativo de lo que necesita una sola muestra, no de las 20 juntas. Se le dejó margen (100GB) sobre esa medición real.
