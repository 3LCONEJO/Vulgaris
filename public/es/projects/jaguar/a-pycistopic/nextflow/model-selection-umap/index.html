Nextflow / MODEL SELECTION UMAP

MODEL SELECTION UMAP

tipo/procesojob/mediumenv/pycistopic

nf/modules/a_pycistopic/model_selection_umap.nf

Envuelve 07_model_selection_umap.py (selección de modelo, Leiden, UMAP). Mismo patrón state/cp de siempre, label 'medium_job' genérico (sin withName: propio, a diferencia de los dos módulos anteriores).

Un flag condicional más

def select_model_flag = params.select_model ? "--select-model ${params.select_model}" : ""

Mismo patrón que ya se vio en PSEUDOBULK EXPORT para --variable — Groovy plano dentro del bloque script, antes de las comillas triples, arma el flag condicionalmente según el parámetro.

Por qué este módulo no necesita ningún archivo puntual como input

A diferencia de otros pasos, 07_model_selection_umap.py no recibe el nombre de ninguna muestra puntual — escanea state/ buscando CADA *_cistopic_obj_models.pkl que haya (el merged de COMBINE_MODELS, y el merged_annotated de COMBINE_MODELS_ANNOTATED cuando este mismo proceso se reusa vía alias para esa rama — ver Workflow & Main) y los procesa uno por uno él solo. Por eso el proceso de Nextflow solo necesita el state_in completo como input — no hace falta declarar canales separados por muestra, porque el script mismo ya sabe descubrirlas.

publishDir con pattern sobre una carpeta anidada: no funciona (bug real, ya corregido)

Primer intento (lo que este módulo tenía hasta el [2026-09-07]): pasarle --figures-dir state/4_figures_tmp (una subcarpeta DENTRO de state, que ya es un output declarado) y agregar un segundo publishDir con pattern: "state/4_figures_tmp/*.pdf" para copiar esos PDFs aparte a 4_figures/<run_date>/A_pyCisTopic/. Corrió sin ningún error — y no publicó NADA. El bug quedó escondido porque el primer publishDir (sin pattern) sí copiaba state entero a 3_output/, así que los PDFs no se perdieron, solo nunca llegaron a 4_figures/ como debían (encontrado recién el [2026-09-08/09], revisando por qué faltaba merged_umap_predicted.l1.pdf en 4_figures/).

Probado aparte con un mini-script Nextflow (nextflow.enable.dsl=2, executor local, sin LSF de por medio) para aislar la causa exacta:

output:
path "state", emit: state
path "state/figs", emit: figs   // anidado DENTRO de "state"

publishDir "out_figs", mode: 'copy', pattern: "state/figs", saveAs: { fn -> '.' }

Resultado: out_figs queda vacío, sin importar si pattern es "state/figs", "state/figs/**", o si se declara state/figs como su propio emit. pattern en publishDir solo matchea outputs de nivel superior que no estén contenidos dentro de otro output ya declarado — aquí state ya “absorbe” a state/figs, y el segundo publishDir no tiene nada que ofrecer. Cambiando state/figs por un directorio hermano de state (no anidado) en el mismo mini-script, el mismo pattern/saveAs funcionó de inmediato.

Fix real (el que tiene el módulo hoy): figures_out es un directorio hermano de state, no una subcarpeta suya:

output:
path "state", emit: state
path "figures_out", emit: figures

publishDir "${params.project_root}/3_output/${params.run_date}/A_pyCisTopic", mode: 'copy', pattern: "state"
publishDir "${params.project_root}/4_figures/${params.run_date}/A_pyCisTopic", mode: 'copy', pattern: "figures_out", saveAs: { fn -> '.' }

Dos detalles de sintaxis que no son obvios:

  • pattern: "state" en el primer publishDir ahora es necesario — sin restringirlo, ese publishDir (que no tenía pattern) publicaría TAMBIÉN figures_out a 3_output/, duplicando contenido sin necesidad.
  • saveAs: { fn -> '.' } es el truco para “aplanar”: cuando el output matcheado es un directorio completo (no un archivo suelto), fn que recibe saveAs es el nombre del directorio mismo ("figures_out"), UNA sola vez — no se invoca por archivo interno. Devolver '.' le dice a Nextflow “copiá el CONTENIDO de este directorio directo en el destino”, en vez de crear 4_figures/.../figures_out/ de más.
