MERGE AND MODEL

tipo/procesojob/customjob/lightenv/pycistopic

merge_only.nf

fit_one_topic.nf

merge_topic_states.nf

combine_models.nf

Estos 4 módulos son lo que hoy hace el trabajo del viejo merge_and_model.nf (un solo proceso, MERGE_AND_MODEL — sigue en el repo, ya NO se usa en pycistopic.nf, dejado solo de referencia histórica). Se documentan juntos aquí porque ninguno tiene sentido leído aislado — son las 4 piezas de un mismo rediseño.

Recursos: MERGE_ONLY/FIT_ONE_TOPIC tienen un withName: propio en nextflow.config (job/custom — 300GB, 24h, cola basement, ver Nextflow Config); MERGE_TOPIC_STATES/COMBINE_MODELS heredan label 'light_job' sin cambios (job/light) — combinar carpetas o reempaquetar pickles ya existentes es barato, ajustar Mallet no.

Por qué el viejo diseño (un solo proceso) se abandonó

06_merge_and_model.py fusiona los *_cistopic_obj_noDBL.pkl de las 20 muestras en un objeto combinado, y después ajusta Mallet para CADA valor de la grilla de n_topics (2, 5, …, 50 — 11 valores) — MERGE_AND_MODEL corría los 11 ajustes uno atrás del otro, dentro de un solo job de LSF. La documentación oficial de pycisTopic recomienda explícitamente lo contrario para datasets grandes (“Parallel LDA with MALLET… si estás en un cluster, te recomendamos someter un job por modelo para que corran simultáneamente”) — medido contra este objeto real (177,332 células), los 11 ajustes secuenciales hubieran tardado ~85h; en paralelo, el total queda acotado por el más lento (n_topics=50, ~23h). Una diferencia real de días, no de minutos.

El problema real que hizo falta resolver para paralelizar esto

06_merge_and_model.py no separa limpio “mergear” de “ajustar el primer modelo”: en su main() —

already_done = [n for n in args.n_topics if _is_valid_file(_topic_model_path(...))]
to_fit = [n for n in args.n_topics if n not in already_done]
if not to_fit:
    _write_combined_pickle(args, already_done, new_models=[])
    return  # <- si to_fit esta vacio, ni siquiera mira si el merge existe

path_merged_nobl = ...
if _is_valid_file(path_merged_nobl):
    # carga el merge YA HECHO
else:
    merged_obj = merge(...)   # <- solo llega hasta aca si to_fit NO esta vacio
    ...
# a partir de aca, ajusta Mallet para los n_topics en to_fit

Para que el script llegue al bloque que llama a merge(), la llamada SIEMPRE tiene que traer al menos un n_topics para ajustar — no existe un modo “solo mergea, no ajustes nada”. Eso significa: la PRIMERA vez que se corre para un merge_name dado (merged_cistopic_obj_noDBL.pkl no existe todavía), esa llamada queda obligada a hacer DOS cosas en el mismo job: mergear los 20 objetos Y ajustar el n_topics que se le pasó — no se pueden separar en dos jobs de LSF distintos sin tocar el script.

merge_only.nf — carga con ese costo inevitable, usando el n_topics más barato

${params.conda_env}/bin/python .../06_merge_and_model.py \
    --out-dir state --mallet-path ... --temp-dir tmp_mallet_2 \
    --merge-name ${params.merge_name} --n-topics 2 --skip-combined-pickle

Le pasa --n-topics 2 (el valor más barato de la grilla) — así el costo extra de mergear se paga UNA sola vez, junto al ajuste más rápido posible. --skip-combined-pickle evita que este proceso también intente escribir merged_cistopic_obj_models.pkl (eso lo hace combine_models.nf, al final, una vez que existen los 11 Topic<n>.pkl).

fit_one_topic.nf — las 10 restantes, parejas, sin el costo del merge

input:
val n_topics
path state_in, stageAs: 'state_in'

Por cada valor en Channel.of(5, 10, 15, 20, 25, 30, 35, 40, 45, 50) (ver Workflow & Main), una llamada independiente con --n-topics ${n_topics}. Como estas 10 llamadas reciben el state_in que YA tiene merged_cistopic_obj_noDBL.pkl (escrito por merge_only.nf), el chequeo _is_valid_file(path_merged_nobl) del script encuentra el archivo, lo carga, y salta derecho a ajustar SU n_topics — ninguna de las 10 paga el costo del merge. Aislamiento de --temp-dir por valor de n_topics (tmp_mallet_${n_topics}) por el mismo motivo que BUILD CISTOPIC OBJECTS ya necesitó aislar el suyo: LDAMallet escribe corpus.txt/corpus.mallet con nombre FIJO, sin sufijo por proceso — 10 tareas paralelas compartiendo un /tmp se pisarían el corpus entre sí.

Dato real medido contra este objeto: t(K) ≈ 9.8h fijo + 16.2min/tópico — ~10h para n_topics=5, ~23h para n_topics=50. También real: 300GB de memoria (100GB murió con TERM_MEMLIMIT, pico real 130-141GB), -n 10 (el pico de CPU real nunca superó 8 cores aunque Mallet pida 12 — su Gibbs sampler paralelo sincroniza conteos compartidos entre threads, limitando el paralelismo real), y SIN avx512 (nada aquí lo necesita, pedirlo excluiría ~36% de los hosts grandes de la farm sin ningún beneficio).

merge_topic_states.nf — juntar las 11 salidas (1 de merge_only + 10 de fit_one_topic)

MERGE_TOPIC_STATES(MERGE_ONLY.out.state.concat(FIT_ONE_TOPIC.out.state).collect())

.concat() encadena dos canales en uno (primero lo que emite MERGE_ONLY, después las 10 de FIT_ONE_TOPIC) — collect() recién dispara MERGE_TOPIC_STATES cuando las 11 terminaron. El proceso en sí es el mismo patrón “combinar carpetas casi idénticas” que MERGE CISTOPIC STATES ya usaba para las 20 muestras — mismo stageAs: 'topic_state_*' + cp -rnL no-clobber, nada nuevo de sintaxis aquí, solo se repite porque junta el output de un paso distinto del DAG.

combine_models.nf — el paso barato final, no un “merge” de verdad

${params.conda_env}/bin/python .../06_merge_and_model.py \
    --out-dir state --mallet-path ... --temp-dir tmp_combine --merge-name ${params.merge_name}

Sin --n-topics (usa la grilla default completa) ni --skip-combined-pickle. Para este punto, los 11 Topic<n>.pkl YA existen en state/2_mallet_model/ (gracias a merge_topic_states.nf) — la lógica de resumibilidad del script (already_done/to_fit) ve que los 11 ya están, así que to_fit queda vacío y el script solo entra a _write_combined_pickle(): carga los 11 Topic<n>.pkl sueltos, los mete en una lista de Python, y guarda esa lista como merged_cistopic_obj_models.pkl. El nombre “combine” viene de ESTE reempaquetado (11 pickles sueltos → 1 pickle con una lista de 11), no de fusionar/promediar modelos — nadie hace eso. Es el motivo por el que este proceso es barato (segundos) comparado con merge_only.nf/fit_one_topic.nf (horas): no ajusta nada de Mallet, solo carga y empaqueta.
