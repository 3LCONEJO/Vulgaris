Nextflow / FILTER ANNOTATED CELLS

FILTER ANNOTATED CELLS

tipo/procesojob/customenv/pycistopic

nf/modules/a_pycistopic/filter_annotated_cells.nf

Primer nodo de la rama “solo anotadas” — la primera vez que este workflow bifurca de verdad, en vez de solo hacer fan-out-y-volver-a-juntar (ver Workflow & Main, sección “Bifurcar el DAG”, para la mecánica de canales). Este artículo cubre el porqué y el diseño; ese otro cubre la sintaxis que lo conecta.

Motivación real

El objeto merged (177,332 células) trae pegada la metadata externa de gene-activity/label-transfer (predicted.l1, vía add_cell_data() en 05_build_cistopic_objects.py, por muestra, antes del merge). No toda célula que pasa el QC propio de ATAC de este pipeline (pasos 03/04) tiene fila correspondiente en esa metadata externa — viene de un filtrado EXHAUSTIVO de ATAC hecho aparte, para el paso de gene-activity/label-transfer puntual. Medido en la corrida real: 63,296 de las 177,332 células (35.7%) quedan con predicted.l1 nulo. El Leiden que calcula este mismo pipeline no tiene ese problema (se calcula fresco sobre las células que hay, sin ningún join externo) — por eso el UMAP de Leiden muestra las 177k y el de predicted.l1 solo 114k.

La pregunta que motivó esta rama: ¿el modelo de tópicos (Mallet) debería haberse ajustado solo con las 114k “confiables”, en vez de con las 177k? “Confiable” aquí NO es un criterio de otro dominio (RNA) — predicted.l1 también sale de ATAC (gene activity), solo que de un filtrado más exigente que el de este pipeline. Filtrar el plot de un modelo ya entrenado con las 177k no responde esa pregunta (los tópicos en sí siguen llevando la influencia de las 63k descartadas) — la única forma real de sacarlas del análisis es reentrenar Mallet sin ellas, que es exactamente lo que hace esta rama completa.

Por qué corre DESPUÉS del merge, no antes

predicted.l1 se pega por muestra en el paso 05, ANTES del merge — en teoría se podría filtrar antes de mergear (por muestra) o después (sobre el objeto ya mergeado): el resultado final (mismas 114k células, mismas regiones) es idéntico en ambos órdenes, porque merge() de pycisTopic no depende de qué células tiene cada muestra, solo concatena matrices. Filtrar DESPUÉS es más barato: es un proceso nuevo sobre un objeto que MERGE_ONLY ya armó, en vez de tocar (e invalidar el cache de) las 20 corridas de BUILD CISTOPIC OBJECTS que ya estaban hechas.

Por qué esto NO llama a merge() de pycisTopic

script:
"""
mkdir -p state
${params.conda_env}/bin/python .../filter_annotated_cells.py \\
    --input state_in/merged_cistopic_obj_noDBL.pkl \\
    --output state/merged_annotated_cistopic_obj_noDBL.pkl \\
    --annotation-column ${params.annotation_column}
"""

filter_annotated_cells.py solo hace .subset() (la misma llamada que 05_build_cistopic_objects.py ya usa para sacar dobletes) — el merge ya está hecho, esto lee su resultado. Esto importa para el diseño de FIT_ONE_TOPIC_ANNOTATED: como merged_annotated_cistopic_obj_noDBL.pkl queda escrito SIN que ningún ajuste de Mallet haya corrido todavía, las 11 llamadas de esa rama (2, 5, 10, …, 50) pueden lanzarse TODAS parejas desde el arranque — a diferencia de MERGE_ONLY/FIT_ONE_TOPIC (la rama original), donde 06_merge_and_model.py no puede separar “mergear” de “ajustar el primer modelo” (ver MERGE AND MODEL), y por eso esa rama quedó partida asimétrica (1 + 10).

Sintaxis: state liviano, no heredado

input:
path state_in, stageAs: 'state_in'

output:
path "state", emit: state

A diferencia de MERGE_ONLY/FIT_ONE_TOPIC/etc. (que hacen cp -rL state_in state, heredando TODO el árbol acumulado: las 20 muestras, su QC, sus PNGs de Scrublet…), aquí el state de salida es deliberadamente liviano — mkdir -p state vacío, más el ÚNICO archivo nuevo que este proceso escribe. Motivo: esta rama nunca publica en el mismo 3_output/.../A_pyCisTopic que la rama original con contenido superpuesto, así que no hay ninguna razón para cargar con esa herencia — y evita cualquier riesgo de colisión de publishDir (el mismo tipo de bug real que ya afectó a MERGE_CISTOPIC_STATES/QC_RUN_ONE_SAMPLE, ver MERGE CISTOPIC STATES y Publishdir Replace Not Merge). Como consecuencia, state_in aquí solo se usa para LEER un archivo puntual (state_in/merged_cistopic_obj_noDBL.pkl), nunca se copia entero.

Recursos: por qué 100GB para un simple .subset()

El .pkl de entrada mide ~20GB serializado. Aunque la operación en sí (.subset()) es conceptualmente simple, deserializar (pickle.load) y copiar el subconjunto puede pedir bastante más que el tamaño del archivo de forma transitoria — el label light_job genérico (16GB) casi seguro no alcanza. nextflow.config le da un withName: propio con 100GB/3h, conservador para una tarea que en teoría tarda minutos.
