TOPIC QC CORRELATION ANNOTATED

tipo/procesojob/mediumenv/pycistopic

nf/modules/a_pycistopic/topic_qc_correlation_annotated.nf

Envuelve analyze_topic_qc_correlation.py — un script que el propio repo original describe como “one-off analysis, not part of run_pipeline.sh”: la referencia real en 4_figures/2026-08-21/A_pyCisTopic/topic_qc_correlation/ se generó corriéndolo a mano vía job_sub_topic_qc_correlation.sh (un bsub directo), nunca pasó por el pipeline principal. Este módulo lo agrega a Nextflow por primera vez — pero solo para la rama “solo anotadas”, no para la original.

Qué responde

Cada tópico tiene un patrón de carga por célula (visible en merged_annotated_topic_umap.png, de BINARIZATION_TOPIC_QC_ANNOTATED) — ¿ese patrón se explica por covariables técnicas de QC (profundidad de secuenciación, TSS enrichment, FRiP, duplicación, score de doblete…) o por identidad celular real (predicted.l1/l2, cluster de Leiden)? Un tópico que correlaciona fuerte con “profundidad de secuenciación” y nada con tipo celular es sospechoso (probablemente técnico, no biológico); uno que separa limpio por tipo celular es lo que se espera de un buen tópico.

Por qué dos inputs, no uno

input:
path state_in, stageAs: 'state_in'
path shared_resources, stageAs: 'shared_resources'

El script necesita tss.bed (test de proximidad a promotor para --focus-topic) y consensus_peak_calling/MACS/*.narrowPeak (test de amplitud cross-tipo-celular) — ninguno de los dos vive en el state LIVIANO de esta rama (ver FILTER ANNOTATED CELLS: no hereda nada de antes del merge). En vez de volver pesado el state de toda la rama para cargar con archivos que ya existen en otro lado, se le pasa merge_only_state — el MISMO value channel que ya alimenta a FIT_ONE_TOPIC/FILTER_ANNOTATED_CELLS en pycistopic.nf — como un segundo input aparte, solo para leer esos dos recursos puntuales. Ejemplo real de por qué conviene tener un value channel (first()) guardado en una variable en vez de encadenarlo una sola vez: aquí se reusa por TERCERA vez en el mismo workflow.

--data-dir/--figures-dir explícitos, otra vez el mismo motivo

analyze_topic_qc_correlation.py, igual que 07_model_selection_umap.py antes del fix (ver MODEL SELECTION UMAP), deriva su propia fecha de corrida leyendo el os.path.realpath() de --cistopic-obj cuando --data-dir/--figures-dir no se pasan explícitos — asumiendo una estructura real 3_output/<fecha>/A_pyCisTopic/... del filesystem. Adentro del work-dir efímero de una tarea de Nextflow, ese realpath resuelve a la carpeta hash de la tarea (tmp_scratch/nf-real-work/xx/yyyy...), no a una fecha real — por eso aquí se pasan siempre explícitos (--data-dir state --figures-dir figures_out), sin confiar en el default del script.

publishDir a A_pyCisTopic_annotated/, no a A_pyCisTopic/

Ver Publishdir Replace Not Merge para el porqué completo: publicar el state (liviano) de esta rama al mismo destino que usa la rama original REEMPLAZARÍA (no fusionaría) los archivos ya publicados de esa rama. Por eso, desde que se descubrió ese bug, TODOS los procesos de la rama anotada que publican su state completo (MERGE_TOPIC_STATES_ANNOTATED, MODEL_SELECTION_UMAP_ANNOTATED, BINARIZATION_TOPIC_QC_ANNOTATED, y este) usan A_pyCisTopic_annotated/ como destino — una carpeta hermana, nunca compartida.

--focus-topic: se dejó el default del script (Topic3), no la lista completa de la referencia

La corrida de referencia (2026-08-21) tiene topic_region_character_Topic<n>.png para muchísimos tópicos (no solo 3) — seguramente se le pasó FOCUS_TOPICS explícito al invocar el script a mano esa vez. Aquí se dejó el default (--focus-topic sin pasar, que el script resuelve a [3]) para no inventar una lista arbitraria de “todos los tópicos que importan” sin que el usuario lo pida — si hace falta caracterizar más tópicos específicos, es un flag más (--focus-topic 5 --focus-topic 12 ...) para agregar al script: de este módulo cuando se sepa cuáles.

  • Publishdir Replace Not Merge — el hallazgo que motivó el destino A_pyCisTopic_annotated/.
  • Workflow & Main — merge_only_state como value channel reusado por varios consumidores.
