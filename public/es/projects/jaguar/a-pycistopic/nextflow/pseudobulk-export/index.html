Nextflow / PSEUDOBULK EXPORT

PSEUDOBULK EXPORT

tipo/procesojob/customenv/pycistopic

nf/modules/a_pycistopic/pseudobulk_export.nf

Envuelve 01_pseudobulk_export.py — el primer paso de la rama A_pyCisTopic propiamente dicha. Es el módulo donde aparece por primera vez el patrón state, que se repite en los otros 8 módulos de esta rama — vale la pena entenderlo bien aquí.

El problema que resuelve state

run_pipeline.sh (el driver de bash que ya existía) pasa la MISMA $OUT_DIR a los 9 pasos, uno atrás del otro — cada script lee lo que dejó el anterior y agrega lo suyo, todo en una sola carpeta que va creciendo.

Nextflow no funciona así por defecto: cada proceso corre aislado en su propio directorio de trabajo (work/xx/yyyy.../), sin ver los archivos de otros procesos a menos que se los pases explícitamente como input:. Los scripts de este repo, sin embargo, siguen esperando una sola carpeta compartida y creciente.

La solución de este piloto: en vez de intentar reescribir 9 scripts para que hablen entre sí “a la Nextflow” (con inputs/outputs finitos y explícitos por archivo), se les da lo que ya esperan — una carpeta llamada state que se va copiando de proceso en proceso, cada vez un poco más llena. Es una simplificación deliberada (ver CONSENSUS PEAK CALLING para el porqué del cp, y la nota abajo sobre el costo de esta simplificación).

El proceso

process PSEUDOBULK_EXPORT {
    label 'pycistopic_env'
    label 'medium_job'
    publishDir "${params.project_root}/3_output/${params.run_date}/A_pyCisTopic", mode: 'copy'

    input:
    path cell_data
    path fragment_mapping

    output:
    path "state", emit: state

    script:
    def variable_flag = params.variable ? "--variable ${params.variable}" : ""
    """
    mkdir -p state
    python .../01_pseudobulk_export.py \\
        --out-dir state --cell-data ${cell_data} --fragment-mapping ${fragment_mapping} \\
        --n-cpu ${params.n_cpu} --temp-dir ${params.temp_dir} ${variable_flag}
    """
}

Pieza por pieza

  • input: path cell_data / path fragment_mapping — recibe DOS archivos sueltos (no una carpeta) que vienen de EXPORT_SEURAT_DATA (ver Workflow & Main para cómo se conecta esto en el workflow). Cuando declaras path x como input y le pasas un archivo real, Nextflow lo symlinkea dentro del directorio de trabajo de ESTE proceso, bajo el mismo nombre — por eso ${cell_data} en el script: ya apunta a un archivo local válido, sin que el proceso sepa la ruta original.
  • Es el ÚNICO módulo de la rama sin state_in — al ser el primer paso de A_pyCisTopic, no hay ningún state previo que recibir; por eso mkdir -p state en vez de cp -rL state_in state como en los siguientes 8 módulos.
  • def variable_flag = ... dentro del bloque script: (antes de las """) — esto es Groovy normal, no sintaxis especial de Nextflow. Se usa para armar un flag CLI condicional (--variable X solo si params.variable no es null/vacío) — el mismo patrón <span class="wikilink wikilink--pending" title="nota pendiente: -n "$X"">-n "$X"</span> && ARGS+=(--flag "$X") que ya usa run_pipeline.sh en bash, solo que aquí es Groovy en vez de bash.
  • output: path "state", emit: state — emite la carpeta state COMPLETA (ya con el archivo nuevo que este script agregó adentro) para que el próximo proceso la reciba como su propio state_in.

El costo de esta simplificación (para tener en cuenta)

Como cada proceso emite el state ENTERO (no solo lo nuevo que agregó), y publishDir corre en cada uno de los 9 pasos, el mismo conjunto de archivos se re-copia a 3_output/<fecha>/A_pyCisTopic/state/ una y otra vez, cada vez más grande — funciona bien, pero no es lo más prolijo. Una versión más “pura” de Nextflow declararía cada archivo nuevo como su propio output finito, sin arrastrar toda la carpeta — quedaría para una refinación futura, no bloquea este piloto.
