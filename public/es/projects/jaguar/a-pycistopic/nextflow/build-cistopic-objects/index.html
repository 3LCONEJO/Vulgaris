Nextflow / BUILD CISTOPIC OBJECTS

BUILD CISTOPIC OBJECTS

tipo/procesojob/customenv/pycistopic

nf/modules/a_pycistopic/build_cistopic_objects.nf

Envuelve 05_build_cistopic_objects.py — el paso largo y caro del pipeline (cisTopic objects por muestra + Scrublet + modelos Mallet, grilla n_topics=[2,5,...,50]). Mismo patrón state/cp de siempre; lo que cambia aquí es cómo se le piden recursos de LSF, y desde [2026-09-01], cuántas veces se llama a este proceso — no la sintaxis básica del process en sí.

[2026-09-01] Paralelizado por muestra

Hasta esta fecha este proceso corría una sola vez — un solo bsub — y adentro, 05_build_cistopic_objects.py recorría las ~24 muestras con un for sample_id in fragments_dict: de Python, una detrás de la otra. Los 16 CPU / 200GB que pedía el job los usaba una muestra a la vez, nunca las 24 en simultáneo (paraleliza secuencialmente adentro, no entre muestras).

Ahora pycistopic.nf llama a este proceso una vez por muestra, todas en paralelo:

process BUILD_CISTOPIC_OBJECTS {
    label 'pycistopic_env'
    tag "${sample_id}"
    publishDir "${params.project_root}/3_output/${params.run_date}/A_pyCisTopic", mode: 'copy'

    input:
    val sample_id
    path state_in, stageAs: 'state_in'
    path cell_data
    path fragment_mapping

    output:
    path "state", emit: state

    script:
    """
    cp -rL state_in state
    python .../05_build_cistopic_objects.py \\
        --out-dir state --cell-data ${cell_data} --fragment-mapping ${fragment_mapping} \\
        --sample-id ${sample_id} \\
        ...
    """
}

Dos cosas nuevas aquí:

  • val sample_id — un input que no es un archivo, es un VALOR (un string). Cada vez que por el canal sample_id (armado en pycistopic.nf, ver Workflow & Main) pasa un nombre de muestra distinto, Nextflow dispara una ejecución nueva de este proceso — con su propio bsub — para ese valor puntual.
  • --sample-id ${sample_id} — la flag nueva agregada a 05_build_cistopic_objects.py (antes no existía): filtra el fragments_dict interno a un solo elemento, así el script real hace exactamente lo mismo de siempre pero para UNA muestra, no las 24. Sin esta flag (por default None), el script sigue comportándose exactamente igual que antes — el uso viejo (bash, run_pipeline.sh) no se rompió.
  • tag "${sample_id}" — no cambia la ejecución, solo hace que nextflow log/la consola muestren de qué muestra es cada línea ([a1/b2c3] BUILD_CISTOPIC_OBJECTS (ATLAS07_atac) en vez de un montón de líneas idénticas sin forma de distinguirlas).

El problema que esto introduce: recursos x N de golpe

nextflow.config sigue pidiendo, POR CADA muestra, los mismos 200GB/16 CPU que antes pedía el job único (no hay una medición de cuánta memoria necesita UNA muestra sola — probablemente bastante menos, pero no se perfiló). Sin ningún tope, Nextflow mandaría las ~24 muestras a LSF al mismo tiempo, todas pidiendo 200GB — un pico de ~4.8TB/384 CPU de una sola vez. Con la farm ya congestionada (ver Nextflow Config, la cola basement), eso es insensato. Por eso nextflow.config le agregó maxForks = params.max_parallel_cistopic (default 6) a este proceso: Nextflow arranca como máximo 6 de estas 24 corridas a la vez, y va largando las siguientes a medida que las anteriores terminan — sigue siendo paralelo (mucho más rápido que una a la vez), pero acotado.

Por qué este módulo no tiene label 'medium_job' ni 'light_job'

Los otros módulos usan un label genérico (light_job/medium_job) cuyos recursos se definen una sola vez en nextflow.config. Este proceso, en cambio, tenía un bsub YA MEDIDO y afinado en el run_pipeline.sh de bash original (200GB, 16 CPU, 12h) — en vez de inventar un label nuevo para un caso de uno solo, nextflow.config le apunta DIRECTO por nombre de proceso:

// en nextflow.config
withName: BUILD_CISTOPIC_OBJECTS {
    queue    = 'basement'
    time     = '12h'
    maxForks = params.max_parallel_cistopic
    clusterOptions = "-G jaguar_analysis -n 16 -M 200000 -R 'select[mem>200000 && avx512] rusage[mem=200000] span[hosts=1]'"
}

withName: matchea el proceso por su nombre exacto (BUILD_CISTOPIC_OBJECTS, el mismo que aparece en process BUILD_CISTOPIC_OBJECTS { ... } aquí) — a diferencia de withLabel:, que matchea cualquier proceso que tenga ese label, sin importar el nombre. Ver Nextflow Config para el detalle completo de por qué clusterOptions quedó así (dos bugs reales de esta farm, encontrados probando esto con -stub-run) y por qué la cola pasó de long a basement.

[2026-09-03] Bug real de concurrencia: Mallet pisándose entre muestras

Con las 6 muestras corriendo en paralelo, ATLAS12_atac murió con:

IndexError: index 472794 is out of bounds for axis 1 with size 472341

adentro de pycisTopic/lda_models.py, cargando el resultado de Mallet. Causa real (confirmada leyendo el código vendoreado): LDAMallet arma el corpus de entrenamiento en <temp_dir>/corpus.txt y <temp_dir>/corpus.mallet — nombre fijo, sin sufijo random ni por proceso (a diferencia de los archivos de RESULTADO, <random_label>_state.mallet.gz etc., que sí llevan un sufijo aleatorio). Con --temp-dir apuntando al /tmp compartido (params.temp_dir, el mismo para las 6 corridas paralelas — y /tmp es local a cada NODO físico, no a cada job), dos muestras que caen en el MISMO nodo se pisan el corpus la una a la otra. Peor: LDAMallet.train() tiene reuse_corpus=True por default — si corpus.mallet ya existe (escrito por OTRA muestra), lo reusa tal cual en vez de reconstruirlo, así que una muestra puede terminar entrenando con el vocabulario de otra completamente distinta.

Esto nunca pasaba con el diseño viejo (secuencial, un Mallet a la vez, nunca dos escribiendo /tmp/corpus.txt al mismo tiempo) — es un bug introducido por paralelizar este paso, no algo que ya existiera.

Fix: --temp-dir tmp_mallet en vez de --temp-dir ${params.temp_dir} — una carpeta RELATIVA, creada con mkdir -p tmp_mallet dentro del propio script. Como cada tarea de Nextflow ya corre en su propio directorio de trabajo aislado (tmp_scratch/nf-real-work/<hash>/), una ruta relativa resuelve DENTRO de ese aislamiento — garantiza que ninguna muestra vea el corpus de otra, sin necesitar nombres únicos a mano.

Lo que sigue: juntar las N salidas

Cada corrida paralela hace su propio cp -rL state_in state (copiando TODO lo de antes) y le agrega solo los .pkl de SU muestra — así que quedan N carpetas state casi idénticas, cada una con un puñado de archivos nuevos distintos. MERGE CISTOPIC STATES las combina en una sola antes de pasarle el resultado a MERGE_ONLY (ver MERGE AND MODEL — el viejo MERGE_AND_MODEL, un solo proceso que ajustaba los 11 valores de n_topics secuencial, ya no se usa; reemplazado por MERGE_ONLY + FIT_ONE_TOPIC en paralelo).

Antes, en bash: un bsub armado a mano

Para comparar: en run_pipeline.sh este mismo paso requería componer el bsub manualmente (BSUB_CMD=(bsub -G jaguar_analysis ... bash -c "$JOB_CMD")) y activar conda a mano dentro del comando, y solo había UN bsub para todas las muestras. Aquí, con executor = 'lsf' + conda = ... declarados una sola vez en nextflow.config, alcanza con escribir el proceso como si fuera a correr localmente — Nextflow arma un bsub por cada muestra y activa el entorno por cuenta propia.
