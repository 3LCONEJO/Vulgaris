Nextflow / MERGE CISTOPIC STATES

MERGE CISTOPIC STATES

tipo/procesojob/light

nf/modules/a_pycistopic/merge_cistopic_states.nf

Nuevo [2026-09-01], agregado junto con la paralelización de BUILD CISTOPIC OBJECTS. Es el “punto de sincronización” entre las N corridas paralelas (una por muestra) y el resto del pipeline, que sigue esperando UN solo state para seguir.

El problema que resuelve

Cada corrida paralela de BUILD_CISTOPIC_OBJECTS parte del mismo state_in (QC + consensus peaks + todo lo de antes) y hace cp -rL state_in state, y después le agrega SOLO los .pkl/.png de su propia muestra. Resultado: N carpetas state, casi idénticas entre sí en la parte compartida, cada una con un puñado de archivos nuevos que NO están en las otras (los de su muestra). Hay que combinarlas en una sola antes de que 06_merge_and_model.py (invocado hoy por MERGE_ONLY/FIT_ONE_TOPIC, ver MERGE AND MODEL) pueda escanear el directorio y encontrar los modelos de las 24 muestras juntos — ese script descubre muestras escaneando <out-dir> por el sufijo *_cistopic_obj_models.pkl, así que necesita verlas todas en el mismo lugar.

process MERGE_CISTOPIC_STATES {
    label 'light_job'

    input:
    path states, stageAs: 'sample_state_*'

    output:
    path "state", emit: state

    script:
    """
    mkdir -p state
    for d in sample_state_*; do
        cp -rnL "$d"/. state/
    done
    """
}

stageAs: 'sample_state_*' — el patrón nuevo aquí

Ya se vio stageAs: ‘state_in’ (un nombre fijo, para UN solo path de entrada). Aquí el input (states) no es un path, es una lista de N paths — la que arma collect() en pycistopic.nf (ver Workflow & Main) — y los N vienen todos con el mismo nombre real (state, la carpeta que emite cada corrida de BUILD_CISTOPIC_OBJECTS). Si Nextflow intentara symlinkear las N carpetas con su nombre original dentro de la carpeta de trabajo de este proceso, las 24 se llamarían state y se pisarían entre sí. stageAs: 'sample_state_*' (con un asterisco) le dice a Nextflow: “a cada uno de esta lista, dale un nombre distinto siguiendo este patrón” — Nextflow los deja como sample_state_0, sample_state_1, …, evitando la colisión.

Por qué cp -rn (no-clobber) y no cp -r a secas

La parte “compartida” (QC output, consensus peaks) es idéntica en las 24 carpetas — no hace falta copiarla 24 veces, ni importa cuál de las 24 gane. -n (no-clobber) hace que la PRIMERA copia de un archivo dado se quede como está y las siguientes 23 se salteen sin pisarla — más rápido, y evita cualquier sorpresa si por algún motivo dos copias de “lo compartido” terminaran siendo ligeramente distintas (no debería pasar, pero no cuesta nada ser explícito). Los archivos que SÍ son distintos entre carpetas (los .pkl de cada muestra, con nombres distintos) nunca chocan, así que da igual el orden en que se procesen las sample_state_*. Ver cp.
