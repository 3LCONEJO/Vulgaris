Nextflow / QC GENERATE COMMANDS

QC GENERATE COMMANDS

tipo/procesojob/lightenv/pycistopic

nf/modules/a_pycistopic/qc_generate_commands.nf

Envuelve 03_qc_generate_commands.py — solo genera el archivo de comandos QC (uno por muestra) y deja tss.bed en su lugar. Ya NO los ejecuta — eso ahora lo hace qc_run_one_sample.nf, uno por muestra en paralelo (ver QC RUN ONE SAMPLE). Mismo patrón state/cp ya explicado en CONSENSUS PEAK CALLING.

[2026-09-01] Por qué se separó en dos procesos

Esto arrancó como un único proceso, QC_GENERATE_AND_RUN, que generaba los ~20 comandos Y los corría los 20 secuencial con bash pycistopic_qc_commands.txt, todo dentro de un solo job de LSF:

script:
"""
cp -rL state_in state
mkdir -p state/1_qc
cp -L ${tss_bed} state/1_qc/tss.bed
python .../03_qc_generate_commands.py --out-dir state ... --commands-file state/1_qc/pycistopic_qc_commands.txt
bash state/1_qc/pycistopic_qc_commands.txt   # <- las 20 muestras, una detrás de otra
"""

Contra el objeto real esto casi funcionó pero terminó fallando dos veces: cada muestra tarda ~45-55min real (fragmentos + TSS enrichment sobre ~120,982 células/20 muestras) → las 20 secuenciales son ~15-18 horas, mucho más de lo que aguanta cualquier límite de tiempo razonable de LSF. La primera vez murió por TERM_MEMLIMIT casi al final de 4h reales de cómputo (perdiendo las 4h — un solo job de LSF no es resumible a mitad de camino). Subir memoria/tiempo (segundo intento, 6h/100GB) solo pateó el problema: a las ~5.5h de las 6 permitidas solo 6 de 20 muestras habían terminado.

Se separó en dos procesos, el mismo patrón que ya se usó para BUILD_CISTOPIC_OBJECTS (ver BUILD CISTOPIC OBJECTS): este archivo (barato, genera comandos + copia tss.bed) y QC_RUN_ONE_SAMPLE (una muestra por job LSF, en paralelo).

Lo que le queda a este proceso

process QC_GENERATE_COMMANDS {
    label 'pycistopic_env'
    label 'light_job'          
    publishDir "${params.project_root}/3_output/${params.run_date}/A_pyCisTopic", mode: 'copy'

    input:
    path state_in, stageAs: 'state_in'
    path cell_data
    path fragment_mapping
    path tss_bed
    
    output:
    path "state", emit: state
    
    script:
    """
    cp -rL state_in state
    mkdir -p state/1_qc
    cp -L ${tss_bed} state/1_qc/tss.bed

    python .../03_qc_generate_commands.py \\
        --out-dir state --cell-data ${cell_data} --fragment-mapping ${fragment_mapping} \\
        --commands-file state/1_qc/pycistopic_qc_commands.txt

    if [ ! -f state/1_qc/tss.bed ]; then
        echo "ERROR: ..." >&2
        exit 1
    fi
    """
    
    stub:
    """
    cp -rL state_in state
    mkdir -p state/1_qc
    touch state/1_qc/pycistopic_qc_commands.txt state/1_qc/tss.bed
    """
}

tss.bed como path de verdad (sigue igual que antes)

tss.bed es un input externo que ningún script de este repo genera — se pasa como path tss_bed (desde params.tss_bed, reusando el archivo real de la corrida 2026-08-21, misma referencia hg38) y se copia a state/1_qc/tss.bed UNA sola vez — cada corrida paralela de QC_RUN_ONE_SAMPLE ya lo encuentra en su propio state_in copiado, sin necesitarlo de nuevo.

// en pycistopic.nf
tss_bed = Channel.fromPath(params.tss_bed).first()
QC_GENERATE_COMMANDS(CONSENSUS_PEAK_CALLING.out.state, cell_data, fragment_mapping, tss_bed)

Channel.fromPath(...) convierte una ruta cualquiera en un canal que emite ese archivo una vez; .first() lo vuelve value channel reusable, igual que cell_data/fragment_mapping (ver Workflow & Main).

El stub: de este módulo

Igual que antes: el stub SÍ tiene que crear tss.bed — si no, el if [ ! -f ... ] fallaría incluso en modo -stub-run.
