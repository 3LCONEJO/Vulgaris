La migración a Nextflow / Nextflow Config

Nextflow Config

tipo/config

nextflow.config

La configuración global — separada del código de los procesos a propósito (ver OVERVIEW). Se carga automáticamente por su nombre: Nextflow la busca en el directorio desde donde se ejecuta nextflow run, sin que nada la tenga que importar explícitamente.

Las dos secciones principales

params { ... }

Valores por defecto de TODOS los parámetros del pipeline (rutas, fechas, flags que ya existían en run_pipeline.sh). Cualquiera se puede pisar desde la línea de comandos con --nombre valor (dos guiones, no confundir con las flags del propio Nextflow, que llevan un solo guion: -resume, -stub-run, etc.). Ejemplo: nextflow run main.nf --run_date 2026-09-01.

params {
    project_root = "/lustre/.../GRN"
    seurat_object_path = "/lustre/.../Seurat_atlas_final.rds"
    run_date = new java.text.SimpleDateFormat('yyyy-MM-dd').format(new Date())
    ...
}

params.run_date calcula la fecha de hoy en Groovy (new java.text.SimpleDateFormat... es Java puro — Groovy corre sobre la JVM, así que cualquier clase de Java está disponible) — el mismo default que ya usaba $(date +%F) en bash.

process { ... }

Ejecutor y recursos. Tres formas de apuntar reglas a procesos, de más general a más específica:

process {
    executor = 'lsf'          // aplica a TODOS los procesos
    clusterOptions = "-G jaguar_analysis"

    withLabel: pycistopic_env { conda = params.conda_env }    // a cualquier proceso con ese label
    withName: BUILD_CISTOPIC_OBJECTS { queue = 'long'; ... }  // a UN proceso puntual, por nombre
}

withName: gana sobre withLabel:, que gana sobre las reglas generales del bloque process{} — igual que la especificidad de selectores en CSS, si ayuda la comparación. Ver label para el otro lado de esta relación (cómo un proceso declara sus labels).

Los dos bugs reales de esta farm, encontrados con -stub-run

Ninguno de los dos es un error de sintaxis de Nextflow — son comportamientos específicos del setup de LSF de esta farm (Sanger), documentados aquí porque son el tipo de cosa que puede reaparecer si se vuelve a tocar nextflow.config más adelante sin tenerlos presentes. Aparecieron corriendo -stub-run contra esta farm, no con una simple revisión de sintaxis.

Bug 1 — memory=/cpus= solos no alcanzan

Con solo esto:

withLabel: light_job {
    cpus = 4
    memory = '16 GB'
}

LSF rechazó el submit:

Sorry you have asked for 16384 Mb memory BUT you have a memlimit of 4096 Mbytes.

El wrapper esub de esta farm exige que el -M (límite duro) venga acompañado de un -R rusage[mem=...] (reserva) que lo respalde explícitamente — el -M que Nextflow arma solo, a partir del directive memory=, no alcanza para pasar esa validación.

Bug 2 — clusterOptions con -R propio choca con los directives memory=/cpus=

El intento de arreglo directo (agregar un -R a mano en clusterOptions, dejando memory=/cpus= como estaban) tiró un error distinto:

Syntax Error: Multiple -R resource requirement strings are not supported on
"span", "cu" and "affinity" sections.

Nextflow traduce memory=/cpus= a su propio -R/-M/-n por detrás — si además clusterOptions trae otro -R completo, bsub recibe dos secciones -R con span[hosts=1] repetido, y las rechaza.

La solución que quedó

Para cualquier label/proceso con requerimientos puntuales: no declarar memory=/cpus= en absoluto — armar -n/-M/-R completo a mano, dentro de un solo clusterOptions, igual que ya se hacía en los job_sub_*.sh de bash de este mismo repo:

withLabel: light_job {
    time = '2h'   // esto sí es seguro combinar -- Nextflow lo traduce a -W, sin tocar -R
    clusterOptions = "-G jaguar_analysis -n 4 -M 16000 -R 'select[mem>16000] rusage[mem=16000] span[hosts=1]'"
}

errorStrategy/maxRetries — qué hacer cuando un proceso falla

process {
    errorStrategy = { task.attempt <= 2 ? 'retry' : 'terminate' }
    maxRetries    = 2
}

Regla global: reintentar automáticamente (mismo proceso, mismos inputs, task.attempt sube 1, 2, 3…) hasta 2 veces; si sigue fallando en el tercer intento, terminate. Pensada para fallos transitorios de la farm (un bsub que rebota, un nodo caído) — no para un fallo determinístico (el mismo bug va a fallar los 3 intentos igual).

Hallazgo real, importante: terminate no solo aborta la tarea que falló — mata TODAS las demás tareas de la sesión que estén corriendo o en cola en ese momento, sin importar si tienen algo que ver con la que falló. Esto costó real dos veces: primero con QC_RUN_ONE_SAMPLE (una muestra con TERM_RUNLIMIT mató de rebote a las otras 4 corriendo en simultáneo — ver QC RUN ONE SAMPLE), y después, más caro, cuando DARS_GENE_ACTIVITY (falla real de memoria, no transitoria — 64GB pedidos, 75GB de pico real) mató las 11 tareas de FIT_ONE_TOPIC_ANNOTATED que estaban corriendo en paralelo, una de ellas con 1h32 de cómputo real ya hecho.

Fix para un fallo que se sabe que NO es transitorio (como el de DARS, mientras no se le suba la memoria): errorStrategy = 'ignore' en un withName: puntual — el proceso queda sin completar, pero el resto de la sesión (cualquier otra rama del DAG incluida) sigue hasta el final sin que ese fallo la interrumpa:

withName: DARS_GENE_ACTIVITY {
    errorStrategy = 'ignore'
}

Un withName: con errorStrategy propio gana sobre la regla global del bloque process{} de arriba — la misma especificidad que ya se vio para queue/clusterOptions.

conda.enabled = true

Sin esta línea, la directiva conda = params.conda_env de cada withLabel se ignora silenciosamente y los procesos corren con lo que sea que esté en el $PATH de quien lanzó nextflow run — un olvido fácil de no notar hasta que un proceso falla con un ModuleNotFoundError difícil de ubicar.
