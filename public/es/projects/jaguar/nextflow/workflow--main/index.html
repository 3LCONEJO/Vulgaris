La migración a Nextflow / Workflow & Main

Workflow & Main

tipo/workflow

main.nf

nf/workflows/pycistopic.nf

Donde se conectan los procesos entre sí. Si ya se leyeron los módulos anteriores, esto es lo último que falta para tener el mapa completo.

main.nf — casi vacío a propósito

#!/usr/bin/env nextflow
nextflow.enable.dsl = 2

include { PYCISTOPIC } from './nf/workflows/pycistopic.nf'

workflow {
    PYCISTOPIC()
}

nextflow run main.nf siempre busca un workflow SIN NOMBRE (el bloque workflow { ... } de aquí, sin identificador) como punto de entrada — es el equivalente a if __name__ == "__main__": de Python. Todo lo real vive en PYCISTOPIC (con nombre), importado de otro archivo. Esto es lo que después va a permitir, en fases siguientes (C_cicero, D_integrate, G_scglue), tener un main.nf que llame a VARIOS workflows con nombre, uno por rama, sin que este archivo crezca mucho.

include { X } from './ruta.nf'

Trae un process o workflow definido en otro archivo — como un import de Python, o un source de bash, pero con nombres explícitos (no todo cae en un namespace global compartido). La ruta es relativa al archivo que hace el include, no al directorio desde donde se corre nextflow run.

nf/workflows/pycistopic.nf — el DAG completo

include { EXPORT_SEURAT_DATA }    from '../modules/b_general/export_seurat_data.nf'
include { PSEUDOBULK_EXPORT }     from '../modules/a_pycistopic/pseudobulk_export.nf'
// ... (7 includes mas)

workflow PYCISTOPIC {

    EXPORT_SEURAT_DATA()

    cell_data        = EXPORT_SEURAT_DATA.out.cell_data.first()
    fragment_mapping = EXPORT_SEURAT_DATA.out.fragment_mapping.first()

    PSEUDOBULK_EXPORT(cell_data, fragment_mapping)
    CONSENSUS_PEAK_CALLING(PSEUDOBULK_EXPORT.out.state)
    QC_GENERATE_COMMANDS(CONSENSUS_PEAK_CALLING.out.state, cell_data, fragment_mapping, tss_bed)

    qc_samples = fragment_mapping
        .splitCsv(header: true, sep: '\t')
        .map { row -> tuple(row.dataset, row.fragment_path) }

    QC_RUN_ONE_SAMPLE(qc_samples, QC_GENERATE_COMMANDS.out.state.first())
    MERGE_QC_STATES(QC_RUN_ONE_SAMPLE.out.state.collect())
    QC_PLOTS_THRESHOLDS(MERGE_QC_STATES.out.state, cell_data, fragment_mapping)

    sample_ids = fragment_mapping
        .splitCsv(header: true, sep: '\t')
        .map { row -> row.dataset }

    BUILD_CISTOPIC_OBJECTS(sample_ids, QC_PLOTS_THRESHOLDS.out.state.first(), cell_data, fragment_mapping)
    MERGE_CISTOPIC_STATES(BUILD_CISTOPIC_OBJECTS.out.state.collect())

    // [2026-09-07] MERGE_AND_MODEL (un solo proceso, ajustaba los 11 valores
    // de n_topics secuencial) ya NO existe -- reemplazado por
    // MERGE_ONLY + FIT_ONE_TOPIC x10 en paralelo + MERGE_TOPIC_STATES +
    // COMBINE_MODELS, ver la sección de fan-out por n_topics más abajo.
    MERGE_ONLY(MERGE_CISTOPIC_STATES.out.state)
    merge_only_state = MERGE_ONLY.out.state.first()
    FIT_ONE_TOPIC(Channel.of(5, 10, 15, 20, 25, 30, 35, 40, 45, 50), merge_only_state)
    MERGE_TOPIC_STATES(MERGE_ONLY.out.state.concat(FIT_ONE_TOPIC.out.state).collect())
    COMBINE_MODELS(MERGE_TOPIC_STATES.out.state)

    MODEL_SELECTION_UMAP(COMBINE_MODELS.out.state)
    BINARIZATION_TOPIC_QC(MODEL_SELECTION_UMAP.out.state)
    DARS_GENE_ACTIVITY(BINARIZATION_TOPIC_QC.out.state, chrom_sizes)

    // [2026-09-08] Rama "solo anotadas", bifurcada del MISMO merge_only_state
    // de arriba -- ver la sección "Bifurcar el DAG" más abajo.
    FILTER_ANNOTATED_CELLS(merge_only_state)
    FIT_ONE_TOPIC_ANNOTATED(Channel.of(2, 5, 10, /* ... */ 50), FILTER_ANNOTATED_CELLS.out.state.first())
    MERGE_TOPIC_STATES_ANNOTATED(FIT_ONE_TOPIC_ANNOTATED.out.state.collect())
    COMBINE_MODELS_ANNOTATED(MERGE_TOPIC_STATES_ANNOTATED.out.state)
    MODEL_SELECTION_UMAP_ANNOTATED(COMBINE_MODELS_ANNOTATED.out.state)
}

(Ver MERGE AND MODEL/MERGE CISTOPIC STATES para el detalle de MERGE_ONLY/FIT_ONE_TOPIC/MERGE_TOPIC_STATES/COMBINE_MODELS, y FILTER ANNOTATED CELLS para la rama “solo anotadas” completa.)

[2026-09-01] Fan-out por muestra: .splitCsv() y .collect()

BUILD_CISTOPIC_OBJECTS pasó de correr una vez a correr una vez POR MUESTRA en paralelo (ver BUILD CISTOPIC OBJECTS para el porqué). Esto trajo dos operadores de canal nuevos, los primeros de este proyecto que no son first():

.splitCsv(header: true, sep: '\t') — de “un archivo” a “una fila por item”

fragment_mapping es un canal que emite UN archivo (el TSV sample_id / dataset / fragment_path). .splitCsv() lo lee y lo convierte en un canal nuevo que emite una fila a la vez, como un dict/mapa por columna (gracias a header: true) — row.dataset, row.fragment_path, etc. .map { row -> row.dataset } se queda solo con la columna que importa aquí (el nombre de la muestra). El resultado, sample_ids, es un canal “de cola” normal con ~24 items — cada uno dispara su propia llamada a BUILD_CISTOPIC_OBJECTS.

Esto lee el fragment_mapping real, generado por EXPORT_SEURAT_DATA en tiempo de ejecución — no hace falta saber de antemano cuántas muestras hay ni sus nombres al escribir el .nf; salen solas del archivo cuando el pipeline corre.

.collect() — lo opuesto de first()

first() toma un canal de UN item y lo vuelve “reusable” (un value channel). .collect() hace lo contrario: toma un canal de VARIOS items (aquí, las N salidas state de las N corridas paralelas, una por cada muestra que termina) y los junta TODOS en una sola lista, emitida como un único item recién cuando el último de los N terminó. Por eso MERGE_CISTOPIC_STATES no arranca hasta que las 24 corridas de BUILD_CISTOPIC_OBJECTS — o cuantas maxForks deje correr nextflow.config a la vez — terminaron todas: es una barrera de sincronización, igual que un wait de bash después de lanzar varios procesos de fondo.

Llamar a un proceso como si fuera una función

EXPORT_SEURAT_DATA() — llamar a un process con paréntesis lo “dispara”. Los argumentos que se le pasan (nada aquí; cell_data/fragment_mapping para los siguientes) tienen que coincidir, en orden, con lo que ese proceso declaró en su bloque input:.

PROCESO.out.nombre_del_emit

Cada process expone sus outputs vía .out — y si el output: usó emit: nombre, se accede como PROCESO.out.nombre (así es como CONSENSUS_PEAK_CALLING(PSEUDOBULK_EXPORT.out.state) sabe agarrar justo el output llamado state de PSEUDOBULK_EXPORT, y no otra cosa).

first() — de canal de un solo uso a valor reusable

Esta es la parte menos obvia viniendo de bash, donde una variable se puede leer todas las veces que haga falta. En Nextflow, un canal (lo que emite un proceso) por defecto se consume una sola vez: el primer proceso que lo lee “vacía” ese ítem del canal. Como aquí cell_data/fragment_mapping los necesitan CUATRO procesos distintos (01, 03, 04, 05), hay que convertirlos primero en un “value channel” — uno que retiene su valor y se puede leer tantas veces como haga falta. first() hace exactamente eso cuando el canal en cuestión solo va a emitir un ítem de todos modos (nuestro caso: EXPORT_SEURAT_DATA corre una sola vez, emite un solo archivo por output).

Sin el first(), solo el primer PSEUDOBULK_EXPORT(...) recibiría el archivo — los demás procesos que también piden cell_data se quedarían esperando para siempre (un deadlock silencioso, sin error explícito, lo cual lo hace particularmente difícil de diagnosticar si se omite por descuido).

[2026-09-08] Bifurcar el DAG: un mismo nodo alimentando DOS cadenas

Todo lo de arriba (y lo de BUILD CISTOPIC OBJECTS/MERGE CISTOPIC STATES) es fan-out dentro de una sola cadena: N corridas paralelas que después se vuelven a juntar en un solo state, y la cadena sigue derecho. La rama “solo anotadas” (motivación completa en FILTER ANNOTATED CELLS) es la primera vez que el DAG bifurca de verdad: el mismo state de MERGE_ONLY alimenta DOS cadenas independientes que nunca se vuelven a juntar — la original (177k células) y la nueva (114k, solo las que tienen predicted.l1).

MERGE_ONLY(MERGE_CISTOPIC_STATES.out.state)
merge_only_state = MERGE_ONLY.out.state.first()

FIT_ONE_TOPIC(remaining_topics, merge_only_state)              // cadena 1
FILTER_ANNOTATED_CELLS(merge_only_state)                       // cadena 2

No hace falta ningún operador especial para “bifurcar” — un value channel (first()) ya es reusable por cualquier cantidad de consumidores, así que alcanza con guardarlo en una variable (merge_only_state) y pasárselo a DOS procesos en vez de uno. El DAG resultante literalmente se ramifica en el grafo que arma Nextflow (visible con nextflow run ... -with-dag) — dos flechas saliendo del mismo nodo MERGE_ONLY.

(Nextflow también tiene un operador que se llama .branch{} — pero es para otra cosa: parte las emisiones de UN canal en varios canales según una condición, por ejemplo separar un canal de muestras en “humano” vs. “ratón” según una columna. Lo de aquí es distinto: no se parten emisiones, se reusa el MISMO output completo como input de dos consumidores.)

[2026-09-08] Reusar un proceso en dos ramas: include { X as Y }

MERGE_TOPIC_STATES y MODEL_SELECTION_UMAP no tienen ningún --merge-name/nombre hardcodeado adentro — el primero solo combina carpetas (cp -rn genérico), el segundo descubre qué merges hay por sufijo de archivo. Como no les importa DE QUÉ rama vienen sus inputs, se pueden reusar tal cual para la rama “solo anotadas” con un alias en el include, en vez de copiar el archivo .nf entero con otro nombre:

include { MERGE_TOPIC_STATES }                                     from '../modules/a_pycistopic/merge_topic_states.nf'
include { MERGE_TOPIC_STATES as MERGE_TOPIC_STATES_ANNOTATED }     from '../modules/a_pycistopic/merge_topic_states.nf'
include { MODEL_SELECTION_UMAP }                                   from '../modules/a_pycistopic/model_selection_umap.nf'
include { MODEL_SELECTION_UMAP as MODEL_SELECTION_UMAP_ANNOTATED } from '../modules/a_pycistopic/model_selection_umap.nf'

Mismo archivo, mismo proceso, DOS instancias con nombre propio dentro del workflow — cada include (con o sin as) crea un símbolo independiente que se puede llamar por separado (MERGE_TOPIC_STATES(...) y MERGE_TOPIC_STATES_ANNOTATED(...) corren como tareas de Nextflow completamente separadas, con sus propios work-dirs). FIT_ONE_TOPIC y COMBINE_MODELS, en cambio, sí tienen --merge-name/--mallet-save-dir que dependen de la rama (ver MERGE AND MODEL) — para esos dos no alcanza un alias, hace falta un archivo .nf propio por rama (fit_one_topic_annotated.nf, combine_models_annotated.nf). Regla práctica: si un proceso no tiene nada hardcodeado que dependa de la rama, alias; si tiene algo hardcodeado (y no vale la pena convertirlo en un input de canal para un solo uso extra), archivo propio.

El “hilo” que atraviesa todo: state

Salvo EXPORT_SEURAT_DATA (sin dependencias) y los cuatro procesos que también necesitan cell_data/fragment_mapping, cada llamada sigue el mismo patrón: PROCESO_SIGUIENTE(PROCESO_ANTERIOR.out.state) — una cadena lineal, un state que se va pasando y creciendo de proceso en proceso. Es exactamente el mismo DAG que ya armaba run_pipeline.sh en bash, paso por paso (01→02→03→04→05→06→07→08→09) — solo que aquí queda declarado, no ejecutado imperativamente línea por línea.
