La migración a Nextflow / Stub Run

Stub Run

tipo/validacion

-stub-run — cómo se validó este pipeline sin correr cómputo real.

El problema que resuelve

Correr el pipeline de producción completo (MACS3, modelado Mallet hasta n_topics=50, etc.) es cómputo real de horas — no es algo para probar cada vez que se toca una coma en un .nf. Pero igual hace falta alguna forma de confirmar que el DAG completo (10 procesos, dependencias entre ellos, conda envs, envío a LSF) está bien armado ANTES de comprometerse a una corrida real.

stub: — un bloque alternativo por proceso

Cada módulo de este piloto tiene, además de su script: real, un bloque stub:

process CONSENSUS_PEAK_CALLING {
    ...
    script:
    """
    cp -rL state_in state
    python .../02_consensus_peak_calling.py --out-dir state ...
    """

    stub:
    """
    cp -rL state_in state
    mkdir -p state/consensus_peak_calling
    touch state/consensus_peak_calling/consensus_regions.bed
    """
}

Al correr nextflow run main.nf -stub-run, Nextflow ejecuta el bloque stub: de CADA proceso en vez de script: — hace todo igual, hace el mismo envío a LSF, utiliza el mismo publishDir, y tiene los mismos input/output, pero el “trabajo real” se reemplaza por comandos baratos (touch, mkdir) que solo crean archivos vacíos con los nombres que el output: de ese proceso espera. Así, el proceso siguiente en la cadena recibe algo con la forma correcta y puede seguir, sin que nadie haya tocado el objeto Seurat de 20GB ni corrido MACS3 de verdad.

Por qué esto importa más de lo que parece

Sin -stub-run, la única forma de confirmar que 10 procesos con dependencias cruzadas, tres conda envs distintos y reglas de recursos LSF particulares de esta farm están bien armados sería… correr todo de una (cosa que ya no es una prueba), en producción, y esperar horas para enterarte de un typo en el proceso 7. Con -stub-run, ese mismo typo aparece en segundos.

Concretamente, probar esto reveló dos bugs REALES de configuración de LSF en esta farm (documentados con el mensaje de error exacto en Nextflow Config) — ninguno de los dos habría aparecido con una simple revisión de sintaxis; hicieron falta un envío real a LSF (aunque sea en modo stub) para salir a la luz.

Cómo correrlo

module load cellgen/nextflow/25.04.4
cd /lustre/scratch127/humgen/projects_v2/jaguar_analysis/analysis/jv8/GRN
nextflow run main.nf -stub-run -work-dir tmp_scratch/nf-stub-work \
    --run_date nf-pilot-test --data_date nf-pilot-test

-work-dir apunta la carpeta de cache/trabajo de Nextflow a otro lado que no sea el default (./work/) – útil para no ensuciar la raíz del repo con corridas de prueba.

--run_date nf-pilot-test es obligatorio al probar esto, no opcional. params.run_date/data_date por defecto son la fecha de HOY – sin pisarlos, publishDir escribe directo en 3_output/<fecha-de-hoy>/A_pyCisTopic/, la misma carpeta que usaría una corrida real de producción ese mismo día. Esto ya pasó de verdad en esta sesión (ver más abajo) y hubo que borrar dos carpetas fecha a mano.

Un tercer bug real, encontrado recién al llegar a un envío real a LSF

Los dos bugs de Nextflow Config aparecen con solo construir el comando bsub (falla el submit). Este tercero es más traicionero: el submit se acepta, el job queda PEND, eventualmente corre… y falla en 0.1 segundos de CPU, sin generar NINGÚN log (ni siquiera el .command.log que arma LSF mismo con su propio -o).

Causa: -work-dir apuntaba a /tmp/claude-23142/... — una ruta que solo existe en el host donde corre esta sesión interactiva, NO en los nodos de cómputo de LSF (node-14-24, en este caso). /tmp es local a cada máquina, no una red compartida — a diferencia de /lustre/..., que sí lo es. El job se despachó, el nodo de cómputo intentó escribir su log en una carpeta que ahí no existe, y todo el wrapper de arranque de Nextflow (.command.run) murió antes de producir una sola línea de output.

Cómo se detectó: bhist -l <jobId> mostró Exited with exit code 1. The CPU time used is 0.1 seconds — un fallo casi instantáneo es la pista de que el problema es de entorno/filesystem, no del script en sí (un script real fallando tarda al menos un poco en arrancar Python/R e importar librerías).

La regla que queda de esto: -work-dir (y, en general, cualquier ruta que un proceso de LSF necesite leer o escribir) tiene que vivir en /lustre/... (o cualquier storage compartido real de la farm) — nunca en /tmp de una sesión particular, aunque “andar en el login node” haga parecer que funciona.

Un cuarto incidente real — publishDir sí ensució carpetas de verdad

Con el -work-dir ya corregido (en Lustre), el -stub-run corrió y publishDir hizo exactamente lo que tenía que hacer: copiar los outputs de cada proceso a 3_output/<run_date>/A_pyCisTopic/. El problema es que run_date no se había pisado con --run_date, así que tomó su default (la fecha de HOY) — y esa corrida de prueba terminó escribiendo archivos vacíos de mentira (state/bed_paths.tsv, state/1_qc/tss.bed, etc.) directo en 3_output/2026-08-26/A_pyCisTopic/ y 3_output/2026-08-27/A_pyCisTopic/, carpetas que en cualquier otro día serían las de una corrida real. Se detectó porque el usuario preguntó por resultados de QC reales y esas dos carpetas aparecieron mezcladas con la real (3_output/2026-08-21/) — se confirmó que solo tenían los archivos de stub y se borraron a mano.

Por qué -stub-run no evita esto por sí solo: el modo stub solo cambia QUÉ comando corre (stub: en vez de script:) — no cambia A DÓNDE publishDir escribe. -stub-run protege del cómputo real y de tocar datos de ENTRADA reales (el objeto Seurat de 20GB nunca se lee) — pero no protege, por sí solo, de sobrescribir una ruta de producción real, si esa ruta depende de un parámetro (run_date) que no se pisó. Por eso el ejemplo de arriba ya incluye --run_date nf-pilot-test — no es opcional.
